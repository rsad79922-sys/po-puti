# «По пути» — сквозной аудит надёжности, совместимости и сетевых сбоев (13.11.2026)

## Назначение и границы результата

Проверены актуальные исходники основного GitHub-репозитория (PWA, Android/Capacitor, Node.js, SQLite, Nginx/systemd-файлы, тесты и CI), фотографии консоли и iPhone из переписки и независимая диагностика TCP/TLS, выполненная GitHub Actions. Сравнены документы разработчиков и сообщения о похожих проблемах в открытых форумах.

**Это не доказательство «идеального продукта».** У аудитора нет SSH к работающей Ubuntu, полного вывода установленного `nginx -T`, файлов Android APK/AAB, реального iPhone, продакшен-базы, секретов и доступа к маршрутизаторам. Веб-тесты GitHub Actions выполняются в эмуляции размера iPhone и WebKit на Linux, а не на iOS-устройстве.

## 1. Что подтвердили фактические проверки

1. На iPhone сервис несколько раз нормально открывался, включая маршруты, профиль, поиск и публикацию, затем начинал выдавать белый экран или ошибки «Сервер перестал отвечать».
2. В отдельные моменты `/api/health` с самого iPhone отдавал `200` с `{"ok":true,"backend":"sqlite","version":"0.2"}`.
3. На Ubuntu `systemctl status nginx po-puti` показывал обе службы `active (running)`; локальный HTTPS с правильным именем домена и сертификатом возвращал `200`. Это не доказывает доступность извне.
4. Во внешних измерениях GitHub DNS разрешался в `130.49.129.99` и TCP к `:443` соединялся, однако HTTPS/TLS-запросы повторно истекали по времени — включая прямое обращение к IP с SNI. Это произошло независимо от Wi-Fi/LTE пользователя.
5. В `tcpdump` на Ubuntu входящий TCP SYN и ACK присутствовали. На ряде зависших соединений приходило только 1448 байт данных, при том что первый TLS record указывал размер 1538 байт с заголовком. Отсутствие оставшегося сегмента на видимых участках захвата — **симптом**, а не установленная первопричина. Также зафиксированы ретрансляции FIN и случаи `Send-Q ` около 3794 байт.
6. `journalctl -u nginx` и стандартный `/var/log/nginx/error.log` не показали информативных ошибок в момент наблюдений. Это не значит, что проблема Nginx исключена.
7. Отдельная ранее обнаруженная проблема — искажённая вставка `:` / `/` / кавычек в VNC-команды. Это проблема ввода терминала; синтаксические проверки исходников GitHub проходили. Не переносить эти симптомы на файлы Git без доказательств.

**Текущий уровень уверенности:** проблема на этапе публичного TLS **воспроизведена**; гипотеза о меньшем MTU / потере одного из сегментов ClientHello или ServerHello **не подтверждена экспериментально**. Неоднократный сбой TCP/TLS до HTTP не может быть вызван JavaScript в `www/app.js`; ошибки API после успешного HTTP-запуска — отдельная плоскость.

## 2. Аналоги и техническое сравнение

| Внешний материал | Что описывает | Насколько подходит |
| --- | --- | --- |
| [ingress-nginx #11424](https://github.com/kubernetes/ingress-nginx/issues/11424) | Маршрутизация может ломаться, если TLS ClientHello приходит несколькими TCP-сегментами | В нашем захвате ClientHello также разделён, но сервер использует обычный Nginx, а не упомянутый модуль passthrough: **точный дефект не перенесён** |
| [Server Fault: SSL при малом MTU](https://serverfault.com/questions/1170054/why-does-an-ssl-handshake-fail-due-to-small-mtu) | TLS останавливается на части handshake из-за уменьшенного MTU пути | Совместимо с обрывами больших сообщений, но нужно проверить обе стороны трафика и реальные размеры |
| [iptables TCPMSS manpage](https://man7.org/linux/man-pages/man8/iptables-extensions.8.html) | MSS корректируется в SYN/SYN-ACK | Важное исправление первоначального плана: входящий SYN влияет на **сервер→клиент**, исходящий SYN-ACK влияет на **клиент→сервер** |
| [Node.js SQLite API](https://nodejs.org/api/sqlite.html) | DatabaseSync исполняет запросы синхронно | Наш код делает SQL на общем event loop; тяжёлый `/api/state` может тормозить *HTTP* |
| [MDN: PWA caching](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching) | Service Worker-кэш позволяет показывать shell при отсутствии сети, но нужно версионирование | У проекта worker сейчас intentionally network-only из-за прошлой ошибки, поэтому при отказе HTTPS офлайн-экран не гарантирован |
| [Capacitor Android](https://capacitorjs.com/docs/android) и [отчёт об origin](https://github.com/ionic-team/ionic-docs/issues/4546) | Android WebView на современном Capacitor использует `https://localhost` | В `capacitor.config.json` установлен `androidScheme=https`; `APP_ORIGINS` должен включать `https://localhost` |

## 3. Аудит клиентского кода

**Подтверждённые уязвимые места / регрессии:**

- `www/app.js` использует единый `/api/state`, который целиком возвращает пользователей, поездки, сообщения и **data:image base64** фотографий. Это влечёт крупные ответы по слабой сети и дорогое повторное создание DOM.
- Ранее дедупликация фоновых GET-запросов не гарантировала *новый* снимок после POST: результат предыдущего GET мог скрыть сохранённые изменения. В ветке аудита изменён клиентский refresh с `fresh:true` после мутаций и входа.
- Публикация поездки ещё вызывала `refreshRemote()` без `fresh:true`, после чего пыталась перейти к только что созданной поездке, которая могла отсутствовать в старом снимке. Исправлено в ветке.
- Старые данные сессии / `localStorage` могут быть недоступны в ограниченном браузерном контексте; доступ должен быть через безопасную обёртку, без краха UI. Проверено.
- `navigator.onLine` не гарантирует HTTPS-доступности, а `AbortController` через 12 с лишь сообщает timeout, не определяет место потери пакета.
- `www/sw.js` сейчас **не перехватывает `fetch`** и удаляет legacy-кэши. Это преднамеренно избегает прошлых зависших navigation, но офлайн-сохранение интерфейса не реализовано.
- HTML запускает `/app.js?v=boot12` и `/styles.css?v=boot12`; при использовании Android встроенный `www/config.js` включает общую API-базу `https://vputipoputka.ru`.

**Не реализовано в этом исправлении:** переработка фотографий на отдельные URL/ресайз на сервере, разделение `/api/state` на дельты/пагинацию, offline-first shell, новая схема токенов. Эти изменения затрагивают текущий Android-протокол и требуют отдельной миграции и нагрузочных тестов.

## 4. Аудит Node.js / SQLite

- SQLite работает в WAL, у аккаунтов и поездок есть FK и ограничения, токены в базе хешируются, пароли — через scrypt, права на изменение заявок, сообщения и admin-методы проверяются сервером.
- `state()` до аудита делал `SELECT` **всех профилей с фотографиями** и фильтровал их уже в Node; кроме того, для каждой принятой заявки отдельно обращался к БД за водителем. **Исправлено** выборкой только видимых ID через `WHERE id IN` и единственным `JOIN`.
- Формат календарной даты проверялся только регулярным выражением (невалидные дни типа `2099-02-30` допустимы), время только форматом двух цифр (`29:77`). **Исправлено**.
- Обработка тела >1.1 MB раньше разрушала HTTP-сокет до отправки 413 — браузер видел сетевую ошибку вместо понятного JSON. **Исправлено**, добавлен тест.
- Добавлены обезличенные диагностические сообщения `[api-slow]` и `[api-aborted]`, без IP, запросных параметров, авторизации и тел.
- `DatabaseSync` остаётся синхронным и при тяжёлом `/api/state` может блокировать event loop. В ветке аудита `scryptSync` заменён на асинхронный `crypto.scrypt`, поэтому проверка паролей больше не блокирует остальные HTTP-запросы. Нужны нагрузочные тесты для SQLite и фотографий.
- `/api/state` не пагинирует поездки и отзывы, хранит изображения как data URI; `sessions` истекают, но в текущем коде не удаляются фоновым процессом.
- Сессии браузера хранятся в `localStorage`; для публичной эксплуатации следует переходить на безопасный механизм с защитой CSRF/XSS и миграцией для Android. Не следует объявлять текущую MVP-схему «безопасной для массового запуска».
- Даты и время местных поездок нуждаются в явной временной зоне; сравнение строк даты с UTC «сегодня» неоднозначно для разных регионов РФ.

## 5. Аудит инфраструктуры и деплоя

- `deploy/nginx-po-puti.conf` в GitHub содержит конфигурацию начального **HTTP:80**, а рабочий HTTPS:443 с Certbot изменён непосредственно в `/etc/nginx` на Ubuntu. Полная конфигурация работающего TLS в GitHub **не зафиксирована**, поэтому нельзя утверждать, что она полностью проверена.
- Конфигурация systemd запускает процесс от `poputi`, закрывает системные каталоги, оставляет на запись только каталог SQLite и слушает loopback. Это верное начальное разделение.
- `/var/log/nginx/error.log` практически пуст; для расследования TLS нужны доступный access log, наблюдение `ss`/`tcpdump` и при необходимости короткий период точечного debug. Логи должны исключать токены и личные данные.
- Внешняя проверка HTTPS по GitHub Actions и локальная проверка Ubuntu могут давать противоречивые результаты: это **суть** обнаруженного сбоя, а не ошибка тестов.
- Публикация `git pull` без подтверждённой резервной копии БД и теста восстановления опасна. GitHub не хранит данные работающих пользователей.
- Для воспроизводимого эксперимента создан `deploy/temporary-https-mss-test.sh`, который на **120 секунд** устанавливает **две** обратимые правила TCPMSS для 443 (PREROUTING SYN и OUTPUT SYN-ACK). Перед внесением правил он **требует успешного создания независимого таймера `systemd-run`**, который удалит правила через 150 секунд даже при отключении VNC; обычный выход удаляет их раньше. Скрипт **не запускается автоматически**; он диагностический, а не постоянное решение. До установки на VPS подтвердить отсутствие ранее оставшихся правил.
- Нельзя путать эту диагностику с постоянным решением: если тест MSS улучшит работу, требуется отдельное подтверждение повторных подключений, журналов и долгосрочной стабильности.

## 6. Android и PWA — единая система

- Android сборка берёт интерфейс из `www/` и вызывает тот же публичный REST API, что браузерная PWA. При штатной настройке обе платформы работают с общей SQLite на сервере.
- Серверная настройка должна разрешать CORS `https://localhost`; добавлен интеграционный тест OPTIONS для Android и отказ для незнакомого origin.
- В Git-дереве **нет** актуальной директории `android/` и подписанной релизной APK/AAB. В ветке добавлен CI workflow `android-build.yml`, который успешно сгенерировал Android-оболочку и debug APK (первый успешный прогон 43289537614). Это подтверждает сборку, но **не** работу на реальном устройстве и не заменяет подписанный релиз. Старый архив `releases/po-puti-android-pwa-v02.zip` не использовать.
- Смена JS в GitHub не обновляет уже установленные APK. Нужен выпуск версии Android и проверка на реальном WebView: авторизация, публикация, фото, сообщения, API CORS, ротация/возобновление сети.

- `tests/server-routing.mjs` — дополнен проверкой Android preflight.
- `tests/server-full-flow.mjs` — дополнен запретом некорректных дат/времени.
- `tests/photo-upload.mjs` — дополнен возвратом 413 вместо падения соединения.
- `tests/state-refresh-after-mutation.mjs` — проверяет конфликт между устаревшим GET и успешно завершённым POST.
- `tests/refresh-singleflight.mjs`, `tests/mobile-startup.mjs`, WebKit smoke, фото и API smoke сохраняются.
- Проверка shell-синтаксиса временного сетевого сценария добавлена в GitHub Actions.

Признаки **реальной готовности**: (a) все CI проверки на финальном SHA успешны, (b) на VPS развернут именно этот SHA после SQLite backup, (c) HTTPS доступен из разных внешних сетей в нескольких сериях подряд и при повторном открытии Safari, (d) браузерный и Android-клиенты проходят авторизацию, заявку и публикацию с фото, (e) восстановление SQLite из резервной копии прошло на отдельном сервере. Если хотя бы (c) или (d) не выполнено, продукт пока **не следует называть полностью исправленным**.

## 8. Чего нельзя честно утверждать

- Что сбой TLS уже устранён кодом на GitHub. **Нет**: он воспроизводился до HTTP и может сохраняться после веб-фиксов.
- Что нарушение MTU однозначно установлено. **Нет**: требуется A/B эксперимент в оба направления, возможны другие причины отсутствия полного ClientHello.
- Что конфигурация Nginx на реально работающем VPS целиком совпадает с файлом в репозитории. **Нет**.
- Что WebKit-тесты равны испытаниям настоящего iPhone или Android APK. **Нет**.
- Что сайт «идеален» или готов к массовым пользователям без мониторинга, миграций, испытаний и восстановления данных. **Нет**.
