# Технический аудит «По пути» — 12.11.2026

## Статус и границы проверки

Проверены состав GitHub-репозитория, основные клиентские и серверные исходники, PWA, конфигурация Android/Capacitor, деплой Nginx/systemd, CI и тестовые сценарии. Это ревизия исходников MVP, **не** сертификация безопасности и не доказательство отсутствия ошибок в каждой ветви кода. Доступа по SSH к реальному VPS и к логам конкретного iPhone у аудитора нет.

Исходное состояние перед правками сохранено в ветке `backup/pre-full-audit-20261112`.

## Установленные факты из диагностики

- На iPhone однажды открывался весь интерфейс, включая переходы по разделам.
- В другой попытке Safari показал JSON `{"error":"Файл не найден"}`. Это ответ `serveStatic` из backend для отсутствующего пути. На мобильном скриншоте полный URL не виден, поэтому нельзя доказать, что запрос был именно к `/`.
- На Ubuntu запрос к корню `127.0.0.1:8080/` выдал полноценный HTML, а HTTP-запрос к домену вернул ожидаемый 301 на HTTPS.
- Тесты синтаксиса, аудит разделителей в URL и проверка Nginx проходили; они не исключают ошибки повторного обращения из Safari.
- Ранее Service Worker ошибочно сохранял любые HTML-навигации как `index.html`. Исправлено ещё до этой ревизии: текущий `sw.js` не перехватывает `fetch`, при активации удаляет предыдущий кэш.

## Автоматизированные проверки

- `tests/source-audit.mjs`: синтаксис и разделители в URL, CSS, Nginx, манифест.
- `tests/pwa-bootstrap.mjs`: загрузчик и логика Service Worker.
- `tests/native-config.mjs`: выбор Android / статический Web-режим.
- `tests/server-routing.mjs`: изолированный сервер с временной БД, прямые ссылки, ресурсы, HEAD, API и отсутствие ложной подмены JS на HTML.
- `tests/server-full-flow.mjs`: независимые аккаунты, публикация, идемпотентность, заявки, роль администратора, приватность телефонов, подтверждение, чат и отмена.
- `tests/browser-webkit.mjs`: первый запуск, reload, установленный Service Worker, переход с диагностической страницы и новая вкладка WebKit iPhone-размера.
- Оба CI-workflow `API smoke tests` и `Mobile WebKit startup` запускаются на main. Проверяйте успешность **именно последнего commit**, а не только прошлых запусков.

Все серверные интеграционные тесты используют собственные временные SQLite-базы, а не `/var/lib/po-puti`.

## Не закрытые риски перед полноценным публичным продуктом

1. **Повторное открытие на реальном iPhone** ещё не подтверждено после установки новых исправлений на VPS. Успешный WebKit CI не полностью воспроизводит DNS, Safari, реальное сетевое соединение и старый кэш устройства.
2. **Сессии в `localStorage`**: токен потенциально доступен при XSS. Для PWA нужны HttpOnly-cookie с защитой от CSRF; для Android — защищённое хранилище.
3. **Резервирование и восстановление SQLite**: работающая схема использует WAL; необходима регулярная онлайн-резервная копия и тест восстановления.
4. **Безопасность публичного сервиса**: нужны усиление rate limiting, защита от ботов, модерация, жалобы, политика персональных данных и мониторинг.
5. **Android**: изменение исходника `www/config.js` не меняет уже установленные APK; нужна отдельная сборка и тест на устройстве.
6. **PWA-офлайн**: в целях безопасности текущий Service Worker не возвращает офлайн-кэш. Полноценный офлайн-режим требует отдельного проектирования и мобильных тестов.
7. **Масштабирование**: `/api/state` пересылает много данных (поездки, отзывы, сообщения); впоследствии потребуется пагинация и выборочные API.
8. **Устаревшие артефакты**: `releases/po-puti-android-pwa-v02.zip` и старые инструкции отражают прежний прототип и не должны использоваться для следующей публикации.
9. **Временные зоны и даты поездок**: сервер и мобильный интерфейс используют разные контексты времени; необходимо согласовать timezone и граничные случаи начала/конца поездки.
10. SMS, push, оплата и реальные turn-by-turn-навигационные функции не включены. Это известные ограничения продукта, а не исправленные ошибки.

## Проверка после публикации

1. Убедиться, что выполнен backup производственной SQLite через механизм SQLite `.backup` (не копировать только живой .sqlite без WAL).
2. Из `/opt/po-puti` выполнить `git pull --ff-only`.
3. Выполнить `systemctl restart po-puti` (изменился backend).
4. Запустить `bash deploy/check-live-release.sh`; ожидается `RESULT: all HTTP release checks passed`.
5. В **обычном Safari** открыть `https://vputipoputka.ru/` три раза, закрывая вкладку между открытиями; проверить повторные переходы, вход, поездки.
6. Если снова будет JSON `Файл не найден`, посмотреть `journalctl -u po-puti -n 100 --no-pager` на строки `[navigation-404]`, зафиксировать запрошенный путь и сверить его с открытым URL.
7. Не переписывать файлы и не перезапускать Nginx без новых фактов. При непрохождении проверок использовать сохранённую резервную ветку.

## Главное заключение

**Ошибки прямой маршрутизации, Android-конфигурации, обработки некорректного URL и чрезмерной выдачи профилей исправлены в GitHub.** Сбой повторного открытия на реальном iPhone **пока не объявляется окончательно исправленным**: нужна установка коммита на VPS и подтверждение тремя открытиями Safari.
