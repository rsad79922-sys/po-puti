# Завершение выпуска: подтверждённое состояние и действия владельца

Работа выполняется в существующем проекте `rsad79922-sys/po-puti`, PR #16.
Подключение API в кабинете поставщика не устанавливает ключ в приложение.
Приватные ключи, пароли, рабочая база и архивы не публикуются в GitHub.

## Что реализовано дополнительно

* Одинаковое удаление аккаунта для PWA и Android через общий сервер и SQLite:
  `POST /api/account/delete`, пароль и `confirmation: DELETE_MY_ACCOUNT`.
  Нельзя передать другой userId; единственный администратор обязан передать роль.
  Все сессии и подписки отзываются. Пользователь становится недоступной для входа
  записью без имени, логина, телефона и фотографии; восстановление запрещено.
* Отменяются только будущие отправления владельца и его будущие заявки.
  Чужие объявления и состоявшееся участие сохраняются. Связанные участники видят
  отмену в общем центре уведомлений. Факты, оценки, авторство по техническим ID,
  даты и решения сохраняются; тексты переписки, связанных отзывов и снимков аудита
  обезличиваются. Обычное редактирование/удаление отзывов остаётся запрещено.
* В v6 отдельная миграция делает приватную проверенную копию до транзакции.
  Новые миграции сами не удаляют аккаунты. Старые pending-запросы не исполняются.
* Фото владельца удаляются безопасно по фиксированным путям; чужие общие файлы
  не удаляются. Неудачная физическая очистка повторяется, URL уже возвращает 410.
  Загрузка фото сериализована с удалением; профиль проверяет сессию после записи.
  Ранее кэшированные посторонними браузерами изображения невозможно отозвать.
* Фоновая перерисовка результатов поиска сохраняет ещё не отправленные города,
  дату и положение курсора. Проверяется смена выдачи во время ввода в обеих
  конфигурациях клиента; это устраняет обнаруженный в CI сброс поля поиска.
* В `DATA_DIR/privacy-erasure.jsonl` сохраняется fsync-журнал намерений (0600).
  Он применяется до запуска API и не позволяет старой копии вернуть данные
  удалённого аккаунта. Некорректный журнал останавливает запуск. Сессии блокируются
  также при незавершённом применении записанного намерения. Удаление журнала
  администратором отменит эту гарантию; храните его отдельно от отката БД/кода.
* Подготовлен серверный транспорт RuStore Push по официальному HTTP API:
  `https://vkpns.rustore.ru/v1/projects/{project_id}/messages:send`.
  Подписки `platform=android, provider=rustore` отделены от FCM; service token
  доступен только серверу. Ретраи, очередь, отписка, отзыв при удалении и generic
  lock-screen payload общие. **Это не завершённая нативная интеграция RuStore SDK:**
  текущий APK ещё использует FCM. Реальная доставка без GMS не подтверждена.
  Страницы документации SDK версий 7.5/7.4 возвращали страницу ограничения 429,
  проверенные публичные адреса артефактов — 404; неподтверждённые классы SDK
  не включались в APK. Повторите интеграцию по доступной официальной документации.

## Яндекс Расписания: безопасное включение

Владелец уточнил: ключ уже хранится в GitHub Actions Secrets как
`YANDEX_RASP_API_KEY`. Повторно передавать его не требуется. Workflow
`check-yandex-rasp.yml` получает существующий секрет только в окружение шага,
проверяет copyright, реальный каталог и поиск между публичными городами без вывода
значения ключа/HTML и не сохраняет ключ в артефакты.
Публикация зависит от этой проверки после Verify/Android. Диагностика VPS также
отдельно проверяет секрет на runner: наличие секрета GitHub и файла VPS — разные
проверки. Диагностика не переносит ключ на VPS. При разрешённой публикации workflow
передаёт JSON с ключом непосредственно в stdin закреплённого SSH-соединения;
`deploy/install-rasp-settings.mjs` сохраняет `/etc/po-puti/rasp.env` (root:poputi,
0640), резервирует прежний файл/drop-in и проверяет запуск после restart.
При сбое возвращаются прежние настройки. Ключ не находится в argv, скрипте shell,
публичном конфиге приложения или артефактах. Исходные пользовательские БД/фото
не затрагиваются этой настройкой. Квота приложения по умолчанию 450 запросов за
скользящие 24 часа, временный кэш только в памяти на 1800 секунд. Это консервативные
настройки приложения, а не подтверждение точной квоты кабинета. Они не подключают
платный тариф. При необходимости ограничить сильнее задайте repository variables
RASP_DAILY_LIMIT (1–450) и RASP_CACHE_SECONDS (1–3600).

Проверка VPS 16.11.2026: ключ/квота/TTL и подтверждение условий Расписаний
в проверенных файлах конфигурации не найдены. РСЯ, сведения об операторе,
прежней подписи RuStore и транспорт Android также не найдены. Значения секретов
не выводились; выполнялась только диагностика.

После доставки проверенного кода на VPS выполните в веб-консоли хостинга:

```bash
sudo bash /opt/po-puti/deploy/configure-timetables.sh
```

Скрипт спросит подтверждение бесплатного тарифа, лимит ниже квоты, допустимый
TTL и ключ со скрытым вводом. Одна проверка copyright тоже расходует квоту.
Кандидат проверяется до замены; файл `/etc/po-puti/rasp.env` имеет root:poputi,
0640, отдельный systemd drop-in. При неудачном запуске возвращаются прежние
настройки. Рабочая БД не заменяется, платный fallback отсутствует. Не вставляйте
ключ в командную строку, GitHub, переписку или скриншот терминала.

## РСЯ и сведения об операторе

Нужны четыре действующих ID: два web-места и два Android-места, условия РСЯ,
разрешённые web origins CSP, фактические сведения об операторе/контакте и
утверждённая политика хранения. Поля перечислены в `deploy/features-v5.env.example`.
Оставьте ADS_ENABLED=false до проверки условий и площадок; тестовая реклама не
является подтверждённой монетизацией. Нельзя выдумывать ID или реквизиты.

Приватная проверка только наличия настроек, без изменения и вывода значений:

```bash
sudo node /opt/po-puti/scripts/check-release-settings.mjs \
  /etc/po-puti/po-puti.env /etc/po-puti/routing.env /etc/po-puti/rasp.env
```

Добавьте существующий защищённый файл дополнительных настроек последним
аргументом. Не указывайте отсутствующие файлы. Код 2 означает неполные настройки.
`settingsComplete` не подтверждает юридическую лицензию, подпись APK или устройства.

## Геокодер: фактическое ограничение бесплатной лицензии

Проверен публичный документ [Условия API Яндекс Карт](https://yandex.ru/legal/maps_api/ru/).
Пункт 6.6.1 ограничивает обработку координат геокодера отображением через
JavaScript API Яндекс Карт; п. 5.1.6 допускает ограниченный временный кэш,
п. 6.6.2 указывает 1000 запросов/сутки. Активация бесплатного ключа не подтверждает
право использовать координаты в BRouter и бессрочно сохранять их в поездках.
Один iframe карты сам по себе не подтверждает соответствие этим условиям.

Нужны отдельное письменное разрешение Яндекса для фактической схемы либо
переход на собственный геокодер на открытых данных. Платный тариф автоматически
не подключается. Публичный Nominatim нельзя использовать как неограниченный
autocomplete. Исторические поездки и работающий сервис этой проверкой не меняются.
GEOCODING_LICENSE_CONFIRMED и ссылка на доказательство служат проверке подготовки,
а не заменяют разрешение. До решения полную готовность магазина заявлять нельзя.

## RuStore и испытания

1. Владелец уточнил: предыдущий APK ещё на модерации. Новая сборка заменяет
   отправленный кандидат; опубликованной версии пока нет. Сохранить package name
   и прежний ключ подписи, проверить versionCode и публичный SHA256 сертификата
   отправленного APK. Приватный keystore хранить вне репозитория.
2. Подписать выпуск прежним ключом на защищённой машине. Запустить
   `scripts/check-android-release.mjs` с прежним versionCode и сертификатом;
   инструкция и переменные в FEATURES-V5.md. Debug/unsigned APK не являются релизом.
3. Завершить нативный RuStore Push SDK, создать проект, хранить server token
   только в защищённом серверном файле, получить device token внутри SDK.
   Сервер уже принимает отдельный provider=rustore. Нельзя отправлять его токен
   через FCM или включать сервисный токен в приложение.
4. Проверить установку поверх отправленного на модерацию кандидата без потери данных,
   доставку/дубли/переходы/отписку при закрытом приложении и перезагрузке на
   настоящих устройствах с GMS и без GMS. Сохранить отчёт с SHA APK и моделью ОС.
5. Только после этого утвердить сведения карточки, политику, рекламу и подать
   подписанный APK на модерацию. Сборка на эмуляторе не заменяет эти проверки.

## Восстановление и откат

Остановите сервис и снимите отдельную копию актуальных данных. Не заменяйте live
SQLite при открытых WAL/SHM. Восстанавливайте набор в новом приватном каталоге,
сохраняя самый новый `privacy-erasure.jsonl` из действующего DATA_DIR/отдельной
защищённой копии. Никогда не заменяйте его старым журналом из выбранного архива.
До открытия порта v6 применит журнал, отзовёт сессии, обезличит старые записи и
удалит вернувшиеся файлы. Проверьте integrity_check/foreign_key_check и health.
Архивы с личными данными нельзя публиковать как артефакты GitHub Actions.
Если актуальный журнал утрачен — автоматическое безопасное восстановление
не гарантируется: сначала восстановите журнал из отдельной защищённой копии.

Code rollback не откатывает БД и журнал. При наличии журнала не запускайте старую
версию на восстановленной старой БД до применения v6. Сроки уничтожения старых
архивов и общих legacy-фотографий должен утвердить владелец; массовая очистка
данных/архивов этим обновлением не выполняется.

## Автоматические проверки

`npm run verify`: синтаксис, изолированные API/SQLite/миграции, сборка.
`npm run test:browser`: Chromium/WebKit, реальные формы PWA и Android-моста.
Новые тесты покрывают пароль/чужой ID/последнего администратора, сохранение
чужих данных и оценок, отзыв сессий, физическое удаление фото, повтор журнала
на старой БД и UI удаления. RuStore HTTP проверяется на изолированном провайдере,
без отправки реальным людям. Android CI собирает debug и unsigned release,
проверяет Manifest, совпадение web-ресурсов и настоящий мост на эмуляторе.
Отдельный этап запускает тот же APK на AOSP API 30 с явной проверкой отсутствия
пакета Google Play Services. Он проверяет запуск, интерфейс и Keystore-мост;
его успех не означает доставку реальных push без GMS.
Это отчёт о доступных проверках, а не утверждение о публикации в магазине.
