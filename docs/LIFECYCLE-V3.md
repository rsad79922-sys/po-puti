# Единая версия PWA / Android: установка и приёмка

Применяется к «По пути», appId `ru.poputi.app`. Оба клиента используют `www/`, один HTTP API и SQLite. Android собирается Capacitor из тех же файлов; отдельной модели поездок или рейтинга в нём нет. Палитра и название существующего приложения сохранены. Исходные требования: [ТЗ](specs/unified-lifecycle-v3.md).

## Что изменилось

| Область | Реализация | Проверки |
|---|---|---|
| UTC, длительность, ETA, архив, запрет изменений с выезда | `server/lifecycle.mjs`, `server/server.mjs`, `www/app.js` | `lifecycle-v3`, `api-v3-parity`, `browser-v3-parity` |
| Подтверждение после ETA+1ч, спор, окно 14 суток | те же модули, `server/admin-api.mjs` | границы времени, несовпадение ответов, отсутствие ответов |
| Неизменяемые отзывы, личные сроки +7 суток, отдельные автооценки | SQLite ограничения/триггеры, lifecycle/API/UI | публикация разных авторов, приватность, повтор, гонка, запрет PUT/PATCH/DELETE |
| Единые уведомления, read_at/unreadCount, push | `server/push.mjs`, `www/sw.js`, Capacitor Push Notifications | `push-v3`, API и UI двух клиентов |
| Администратор, причины, пагинация, аудит, решения споров | `server/admin-api.mjs`, общий UI `/admin` | запрет обычному пользователю, серверная команда роли, аудит/приватность |
| Данные и выпуск | миграция/backup, `deploy/*`, Actions | `deployment-safety`, копия БД, Verify, Android APK |

Новая поездка содержит ISO `departureAt` с явным смещением UTC и вручную заданную длительность в минутах. Это честный fallback: маршрутизатор не подключён, расстояние по прямой не выдаётся за ETA. UI показывает смещение времени поездки и источник ETA. С момента отправления запрещены отмена, новые заявки, отмена брони и решения по заявкам — в том числе старым клиентам через API (409). Pending истекают; accepted сохраняются для истории.

Окно ответа начинается в ETA+1ч и длится 14 суток. Ответ неизменяем. «Да» сразу открывает форму. Закрытие формы не отправляет отзыв: его можно открыть снова до личного срока. Каждый ручной отзыв публикуется через 7 суток после **своей отправки**, только при `completed` и без блокировки. Пока он скрыт, доступен автору и администратору. Спор скрывает и ранее опубликованный новый отзыв; его публикация возобновляется после разрешения.

Автооценка создаётся через 7 суток после личного «Да» только для взаимно подтвердившей участие пары, состоявшейся поездки, без ручного отзыва/спора/блокировки. Текст: «Оценка выставлена автоматически». Она не увеличивает средний пользовательский рейтинг и число ручных оценок. Поздняя ручная отправка запрещена. Уникальность пары и неизменяемость закреплены в БД. Старые отзывы сохранены с прежними датами; их модерация хранится отдельно.

Поездки без достоверного legacy ETA не получают выдуманного прибытия или автоматических оценок. Их прежние дата/время консервативно читаются как UTC для блокировки операций; будущие записи требуют явного смещения. Старый backend до v3 не должен работать одновременно с новым: он не знает новых правил, хотя мост обеспечивает технический откат без ошибки SQL.

## Выпуск и миграция

Базовая чистая Ubuntu 24.04, HTTPS, nginx, systemd, журналирование и резервирование описаны в [deploy/README.md](../deploy/README.md). Node 24 обязателен. Не переносите рабочую SQLite или uploads в репозиторий.

1. Перед v3 на существующий VPS установить **compatibility bridge** с явными списками колонок в INSERT для rides/requests/notifications/reports. Основной release-скрипт откажет до остановки сервиса, если установленный backend ещё использует старые позиционные INSERT. Это обеспечивает техническую совместимость автоматического отката после добавления колонок.
2. На ветке кандидата должны пройти `npm ci --ignore-scripts`, `npm audit --audit-level=moderate`, `npm run verify`, браузеры Chromium/WebKit и Android CI.
3. Запустить `Private migration rehearsal` на ветке кандидата. Он повторно проходит Verify, получает SSH только после тестов и на VPS создаёт приватную согласованную копию рабочей SQLite. Живая БД открывается read-only; исходные записи проверяются по хешам до запуска worker на копии, затем integrity/FK/уникальность. Копия остаётся под `/var/backups/po-puti-v3-rehearsal-*` (0700), **не загружается в артефакты**. HEAD production, приложение и uploads не заменяются. Для ручного запуска из проверенного checkout: `sudo bash deploy/validate-lifecycle-copy.sh <40-hex-commit>`.
4. Объединение PR в main запускает существующий автоматический выпуск после reusable Verify. Для чистой установки — ручной `Publish` с подтверждением и `initial_install=true` по deploy README. npm production dependencies устанавливаются из lockfile до остановки сервиса; при откате восстанавливаются прежние node_modules.
5. При первом запуске v3 backend сам сохраняет online SQLite backup в `/var/lib/po-puti/migration-backups/before-lifecycle-v3-*.sqlite`, проверяет integrity и выполняет additive DDL в одной транзакции. Старые строки не удаляются и таблицы не пересоздаются. Версия схемы проверяется при каждом старте. Не запускайте два процесса миграции одновременно.
6. Проверить `systemctl status po-puti`, `journalctl -u po-puti -n 100`, локальный `curl -fsS http://127.0.0.1:8080/api/health` и внешний `curl -fsS https://vputipoputka.ru/api/health`. Затем проверить один аккаунт в установленной PWA и тот же аккаунт в Android. Внешние сбои TLS провайдера требуют отдельной проверки и этим релизом не объявляются исправленными.

Откат скрипта меняет код и зависимости, **не восстанавливает БД поверх живого WAL**. Схема остаётся расширенной; мост допускает работу старого backend, но временно теряются новые ограничения/worker. Предпочтителен оперативный исправляющий выпуск. Полное восстановление данных — отдельная процедура с остановкой сервиса, сохранением текущих DB/WAL/SHM/uploads и проверкой копии; оно может потерять изменения после снимка и не выполняется автоматически.

## Первый администратор

Устаревшие `ADMIN_USERNAME`/`ADMIN_PASSWORD` больше не создают аккаунт. Владелец регистрируется обычным способом; его ID показан в профиле. Через доверенную серверную консоль, из `/opt/po-puti`:

```sh
sudo -u poputi env DATA_DIR=/var/lib/po-puti node scripts/admin-user.mjs --user-id EXISTING_USER_ID --reason 'Владелец проверен через консоль сервера'
```

Команда принимает только существующий ID, делает backup и пишет неизменяемый аудит. `--revoke` снимает роль, кроме последнего администратора. После этого войти заново и открыть `/admin` (в Android `#/admin`). Роль проверяет сервер для каждого API, прямой web `/admin` требует HttpOnly-сессию. Поддерживается миграция прежней cookie при загрузке `/state`. MFA внутри приложения пока нет; ограничьте доступ к консоли/GitHub и включите MFA у провайдера и GitHub.

## PWA Web Push / VAPID

Установить зависимости (`npm ci --omit=dev --ignore-scripts`) и создать ключи на сервере в приватный файл, не в shell history и не в Git:

```sh
sudo install -d -m 0750 -o root -g poputi /etc/po-puti
sudo sh -c 'umask 077; cd /opt/po-puti; node --input-type=module -e '\''import {generateVAPIDKeys} from "web-push"; const k=generateVAPIDKeys(); console.log("VAPID_PUBLIC_KEY="+k.publicKey+"\nVAPID_PRIVATE_KEY="+k.privateKey+"\nVAPID_SUBJECT=mailto:YOUR_ADMIN_EMAIL")'\'' > /etc/po-puti/push.env'
sudo chown root:poputi /etc/po-puti/push.env
sudo chmod 0640 /etc/po-puti/push.env
```

Замените адрес на реальный. Добавьте локальный systemd drop-in через `sudo systemctl edit po-puti`:

```ini
[Service]
EnvironmentFile=/etc/po-puti/push.env
```

`sudo systemctl daemon-reload && sudo systemctl restart po-puti`. Публичный VAPID передаётся API; приватный ключ не отправляется клиентам. Не менять ключи без плана повторной подписки устройств. В профиле нажать «Включить уведомления» явно. При `denied` разрешение изменяется настройками браузера. iPhone требует поддерживаемую iOS и PWA на экране «Домой». Обычная вкладка Safari не считается проверкой фонового push. Цвет/наличие точки задаются ОС/лаунчером.

## Android / Firebase (проект ещё не создан)

1. Создать Firebase-проект, добавить Android app с package `ru.poputi.app`, включить Firebase Cloud Messaging API HTTP v1. Скачать `google-services.json` и положить **только локально** в `android/app/` после `npx cap add android`. Каталог android игнорируется Git.
2. Для CI положить JSON клиентской конфигурации в repository secret `FIREBASE_ANDROID_CONFIG_JSON` (не service account). Workflow передаёт его в native build. При отсутствии секрета тестовый APK собирается без настроенного FCM: наличие APK не доказывает доставку push.
3. Создать отдельный service account с минимальными правами отправки FCM (`roles/firebasecloudmessaging.admin` на нужный проект), сохранить его JSON только на VPS `/etc/po-puti/fcm-service-account.json`, root:poputi 0640. Это **приватный ключ**: никогда не класть в GitHub client-config secret, APK, чат или репозиторий.
4. Добавить в приватный push.env `FCM_PROJECT_ID=<project-id>` и `FCM_SERVICE_ACCOUNT_JSON=/etc/po-puti/fcm-service-account.json` (поддерживается также `GOOGLE_APPLICATION_CREDENTIALS`), перезапустить сервис. Код допускает только service_account JSON совпадающего проекта. `npx cap sync android`, пересобрать APK и установить.
5. Нажать кнопку включения уведомлений, проверить разрешение Android 13+, канал `trip_updates`, доставку в foreground/background/после закрытия и переход по нажатию. Не обещать push после принудительного force-stop ОС: требуется повторный запуск приложения.

Firebase пока отсутствует по ответу владельца. Проверены код, API, очередь и native bridge с имитацией Capacitor; **доставка реальным FCM на телефон и подписанный release APK пока не подтверждены**. Debug APK из CI не предназначен для магазина.

## Worker, диагностика и ограничения

API запускает tick при старте и каждую минуту под существующим systemd; клиенты могут быть закрыты. Точное состояние пересчитывается также при API-запросах. Фактическая отправка/publish в фоне может запоздать до минуты относительно UTC-дедлайна. Уникальные ключи событий/пар защищают от дублей. Outbox имеет lease, до 5 попыток с увеличением интервала; 404/410 отключают подписку. При выходе устройство отключается и ожидающие доставки отменяются. Push имеет общий текст без приватного отзыва/жалобы; запись внутри приложения хранится независимо от разрешения ОС.

`/admin` → «Система», «Доставки», «События», «Аудит» показывает реальные очереди/ошибки/worker. Для разового восстановления отставших задач (не второй постоянный сервис):

```sh
sudo -u poputi env DATA_DIR=/var/lib/po-puti node scripts/run-jobs.mjs
```

Без push.env этот запуск обновит lifecycle, но не доставит push; для доставки запускайте с теми же приватными переменными через доверенный service unit. Не печатать env/токены в журналы.

Остаточные ограничения: `/state` пока без пагинации (admin списки paginated), SQLite на одном локальном VPS, native Bearer хранится прежним WebView-механизмом (переход в Keystore остаётся отдельным усилением), нет MFA в самом приложении и проверки телефона. До массового запуска нужны нагрузочные тесты, политика персональных данных и проверка реальных Android/iPhone. Без настроенных VAPID/FCM центр уведомлений остаётся работоспособным.
